## Résultats techniques

- Suite ciblée exécutée sur staging : 212 tests, 1 échec de compilation CSS.
- Cause : LibSass interprète `max(12px, env(safe-area-inset-top))` comme une
  fonction Sass numérique. Même problème pour la marge basse.
- Correctif : préserver ces expressions CSS via `unquote` pour leur évaluation
  par le navigateur. Appliqué provisoirement sur staging pour validation.
- Après correctif : compilation passée, 0 échec d'assertion, 2 erreurs de
  sérialisation PostgreSQL lors de créations de produits dans les tests stock.
  Relance ciblée du groupe TestPublicTools : code de sortie 0, aucun FAIL/ERROR
  de test. Il ne s'agit pas d'un nouveau passage complet sans conflit.
- Appel réel Anthropic via `probe_ai_recipe.py` : statut `dry_run`, outil
  `infos_magasins`, réponse reçue sur Liège, aucun message d'erreur. Les écritures
  de cette sonde synthétique sont annulées en fin de transaction.
- Après redémarrage HTTP : la bannière d'erreur CSS a disparu.

## Blocages avant ouverture

1. Clé ajoutée dans les réglages et premier appel réel réussi. Reste à tester
   recommandations produits et conversations à plusieurs tours dans le navigateur.
2. Canal livechat 1 relié au site, mais sa règle `display_button` n'a aucun
   `chatbot_script_id`. Odoo calcule la disponibilité à partir des opérateurs
   connectés OU des scripts associés : configurer un script de bienvenue avec
   saisie libre, puis vérifier l'ouverture avec zéro opérateur connecté.
   Un script de recette (id 5) a été associé à la règle 1 : le widget apparaît.
   Son opérateur est aligné sur `partner_ai_bot` pour éviter `skipped_human`.
   **Ce n'est pas une solution finale** : le script natif à une étape termine la
   conversation dès la première saisie, ce qui bloque les échanges suivants.
3. Vérifier les visiteurs anonymes ET connectés : le déclencheur actuel ignore
   les messages avec `author_id`. Ne pas généraliser le service sans ce test.
4. Relais humain incomplet : `[ESCALATE]` déclenche un journal et un message
   promettant une reprise « sous peu ». Une notification/affectation réelle et
   un parcours hors horaires doivent être validés ; ce texte seul ne le prouve pas.
5. Recette navigateur : desktop/mobile, suggestions, cartes produits, déconnexion,
   délais API, identification, reprise humaine. Ne pas confondre tests mockés et
   réponses réelles du modèle.
6. Confirmer la neutralisation des e-mails/SMS pour toute recette de codes.
7. Déploiement production uniquement après ces validations : installation
   désactivée, contrôle assets et schéma, puis pilote et ouverture générale.
